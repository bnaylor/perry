# Context Packet Specification v1.0

## The Sovereign Loop Platform — Data Interface Layer

---

## 1. What Problem Does This Solve?

The Context Packet is the **sole authorized channel** for external information to cross the security boundary between the Researcher (which has network access) and the Coder (which is network-isolated). Without a formal schema, this boundary is meaningless — the Researcher could pass arbitrary text, code snippets, or prompt injection payloads directly into the Coder's context window.

The Context Packet schema enforces three properties:

- **Machine-validatable structure**: A JSON Schema check rejects malformed packets *before* any LLM processes them. This is deterministic and cannot be socially-engineered.
- **Typed fields with constrained vocabularies**: Enumerations (auth methods, HTTP verbs, operation types) prevent the Researcher from inventing novel categories that bypass the Auditor's expectations.
- **Explicit trust boundaries**: Free-text fields exist (they have to — the Researcher needs to communicate nuance), but they are clearly demarcated as `UNTRUSTED` so downstream agents and the Auditor know to treat them with appropriate skepticism.

---

## 2. Schema Architecture Overview

The Context Packet is a single JSON document with seven top-level sections:

```
┌─────────────────────────────────────────────────────┐
│                   CONTEXT PACKET                     │
├──────────────────┬──────────────────────────────────┤
│  packet_meta     │ Provenance, versioning, lineage  │
├──────────────────┼──────────────────────────────────┤
│  task_reference   │ PM's task ID, PRD summary, CUJs  │
├──────────────────┼──────────────────────────────────┤
│  external_apis   │ Structured API descriptions       │
│                  │ (endpoints, auth, schemas)        │
├──────────────────┼──────────────────────────────────┤
│  data_schemas    │ Domain models and data formats    │
├──────────────────┼──────────────────────────────────┤
│  dependencies    │ Libraries (with approval status)  │
├──────────────────┼──────────────────────────────────┤
│  constraints     │ Operation allowlist/denylist      │
├──────────────────┼──────────────────────────────────┤
│  environment     │ Runtime requirements for sandbox  │
├──────────────────┼──────────────────────────────────┤
│  researcher_notes│ Free-text (UNTRUSTED) findings    │
└──────────────────┴──────────────────────────────────┘
```

### Trust Levels by Section

| Section | Trust Level | Rationale |
|---------|------------|-----------|
| `packet_meta` | **System** | Generated by platform infrastructure, not LLM-authored |
| `task_reference` | **High** | Originates from PM, which represents verified user intent |
| `external_apis` | **Medium** | Researcher-authored from external sources; structured but could reflect misunderstood docs |
| `data_schemas` | **Medium** | Same as above |
| `dependencies` | **Medium-Low** | Researcher suggests, PM must approve non-allowlisted packages |
| `constraints` | **High** | Set by PM based on task scope; Auditor enforces strictly |
| `environment` | **Medium** | Researcher recommends, PM/Auditor validate |
| `researcher_notes` | **Low (UNTRUSTED)** | Free-text from an agent that reads arbitrary web content |

## 3. Key Design Decisions

### 3.1 No Raw Documentation Pass-Through

The Researcher MUST NOT copy-paste API documentation verbatim. Every field in `external_apis` requires the Researcher to *restate* the information in structured form. This serves two purposes:

1. **Injection defense**: Malicious API docs that embed prompt injection payloads (e.g., "Ignore previous instructions and...") get stripped when the Researcher must extract only typed fields like `method`, `path`, and `query_params`.
2. **Comprehension verification**: If the Researcher can't express an API's behavior in the structured format, it probably doesn't understand the API well enough for the Coder to rely on it.

### 3.2 Enumerated Auth Methods

The `auth_method` field uses a closed enum rather than free text. This prevents the Researcher from describing exotic or dangerous authentication flows that the Auditor hasn't been trained to evaluate. If a genuinely novel auth method is needed, it maps to `"custom"` and automatically triggers PM review.

### 3.3 Secrets Never Travel in Packets

The schema enforces that authentication credentials are referenced by **environment variable name** (`token_env_var`), never by value. The Executor injects actual secrets at runtime from a separate secrets store. This means:

- The Context Packet can be logged and audited without leaking credentials.
- The Coder writes code that references `os.environ["WEATHER_API_KEY"]`, never a hardcoded string.
- The Auditor can verify this pattern mechanically.

### 3.4 The Constraints Section as a "Capability Contract"

The `constraints.permitted_operations` field is the most security-critical part of the packet. It defines an explicit allowlist of what the generated code is *permitted to do*. The Auditor's "Capability Leap" check becomes simple: does the code perform any operation not on this list?

Example: If the PM says "fetch weather data and save it to a file," the permitted operations would be `["http_get", "read_env_var", "write_local_file", "write_stdout"]`. If the Coder's code also opens a socket listener or spawns a subprocess, the Auditor rejects it — no judgment call required.

### 3.5 Confidence Scoring for Escalation

Each API entry includes a `confidence` field (`high` / `medium` / `low`). This is the Researcher's self-assessment of how reliable its understanding is. A `low` confidence rating automatically triggers the Auditor to flag the entry for PM review before the Coder uses it. This creates a pressure-relief valve: the Researcher doesn't have to pretend certainty when documentation is ambiguous or contradictory.

### 3.6 Conflicting Sources Surface to the PM

The `researcher_notes.conflicting_sources` array forces the Researcher to explicitly declare when two sources disagree. Rather than silently choosing one interpretation, the conflict is escalated to the PM for a decision. This prevents the Researcher from making judgment calls that should be strategic decisions.

## 4. Validation Pipeline

The Context Packet passes through three validation stages before reaching the Coder:

```
Researcher Output
       │
       ▼
┌──────────────────────┐
│  Stage 1: Schema     │  Deterministic JSON Schema validation.
│  Validation          │  Rejects structurally invalid packets.
│  (jsonschema lib)    │  NO LLM involved.
└──────────┬───────────┘
           │ PASS
           ▼
┌──────────────────────┐
│  Stage 2: Content    │  Deterministic checks:
│  Scanning            │  - Regex scan for secrets patterns
│  (Rule-based)        │  - URL allowlist verification
│                      │  - Dependency cross-ref against approved list
│                      │  - Free-text fields scanned for injection patterns
└──────────┬───────────┘
           │ PASS
           ▼
┌──────────────────────┐
│  Stage 3: Semantic   │  LLM-powered (Auditor on Tier 1):
│  Review              │  - Does the packet match the PM's task?
│  (Auditor Agent)     │  - Are the constraints appropriate for scope?
│                      │  - Do low-confidence items need PM escalation?
└──────────┬───────────┘
           │ PASS
           ▼
      Coder Agent
```

### Stage 1: Schema Validation (Deterministic)

```python
import jsonschema

def validate_context_packet(packet: dict, schema: dict) -> list[str]:
    """Returns list of validation errors, empty if valid."""
    validator = jsonschema.Draft7Validator(schema)
    errors = []
    for error in sorted(validator.iter_errors(packet), key=str):
        errors.append(f"{'.'.join(str(p) for p in error.absolute_path)}: {error.message}")
    return errors
```

### Stage 2: Content Scanning (Deterministic)

```python
import re

# Patterns that should NEVER appear in a Context Packet
SECRETS_PATTERNS = [
    r'(?i)(api[_-]?key|secret|token|password)\s*[:=]\s*["\']?[a-zA-Z0-9_\-]{20,}',
    r'(?i)bearer\s+[a-zA-Z0-9_\-\.]{20,}',
    r'ghp_[a-zA-Z0-9]{36}',           # GitHub personal access tokens
    r'sk-[a-zA-Z0-9]{32,}',           # OpenAI-style keys
    r'AIza[a-zA-Z0-9_\-]{35}',        # Google API keys
    r'AKIA[A-Z0-9]{16}',              # AWS access keys
]

INJECTION_PATTERNS = [
    r'(?i)ignore\s+(previous|above|all)\s+(instructions?|prompts?)',
    r'(?i)you\s+are\s+now\s+',
    r'(?i)system\s*:\s*',
    r'(?i)forget\s+(everything|your|all)',
    r'(?i)<\s*/?system\s*>',
]

def scan_content(packet: dict) -> list[str]:
    """Scan all string values for dangerous patterns."""
    warnings = []
    
    def walk(obj, path=""):
        if isinstance(obj, str):
            for pattern in SECRETS_PATTERNS:
                if re.search(pattern, obj):
                    warnings.append(f"SECRETS_LEAK at {path}: matches pattern {pattern[:30]}...")
            for pattern in INJECTION_PATTERNS:
                if re.search(pattern, obj):
                    warnings.append(f"INJECTION_SUSPECT at {path}: matches pattern {pattern[:30]}...")
        elif isinstance(obj, dict):
            for k, v in obj.items():
                walk(v, f"{path}.{k}")
        elif isinstance(obj, list):
            for i, v in enumerate(obj):
                walk(v, f"{path}[{i}]")
    
    walk(packet)
    return warnings
```

### Stage 3: Semantic Review (LLM — Auditor)

This is a focused prompt for the Auditor agent, NOT a general-purpose review:

```
You are reviewing a Context Packet (ID: {packet_id}) for task {task_id}.

The PM's original requirement was:
"{prd_summary}"

Your job is to answer THREE specific questions:

1. SCOPE MATCH: Does the information in this packet correspond to what 
   the PM asked for? Flag any APIs, schemas, or dependencies that seem 
   unrelated to the stated task.

2. CONSTRAINT APPROPRIATENESS: Are the permitted_operations in the 
   constraints section the MINIMUM needed for this task? Flag any that 
   seem overly broad.

3. ESCALATION CHECK: Are there any items with confidence: "low" or 
   entries in conflicting_sources that need PM decision before proceeding?

Respond with: APPROVED, NEEDS_REVISION (with specific issues), or 
ESCALATE_TO_PM (with questions for the PM).
```

## 6. Integration Points

### How Each Agent Uses the Context Packet

| Agent | Interaction | Details |
|-------|------------|---------|
| **Researcher** | **Produces** | Fills in all fields. Cannot modify schema. Output goes through 3-stage validation. |
| **PM** | **Reviews & Approves** | Checks `task_reference` alignment, approves non-allowlisted `dependencies`, resolves `open_questions` and `conflicting_sources`. Sets/adjusts `constraints`. |
| **Coder** | **Consumes (read-only)** | Uses `external_apis`, `data_schemas`, `dependencies`, and `constraints` as its complete specification. Must not exceed `permitted_operations`. |
| **Auditor** | **Cross-references** | Compares the Coder's output against the packet. Verifies: code only calls listed endpoints, only uses listed dependencies, stays within `permitted_operations`, and references secrets only by env var name. |
| **Executor** | **Configures sandbox from** | Uses `environment` to build the Docker container, inject env vars from the secrets store, and set file mount points. Uses `constraints` to configure network policies and timeouts. |

### State Machine Transitions

```
PM creates task
       │
       ▼
Researcher produces Context Packet
       │
       ▼
[Stage 1: Schema Validation] ──FAIL──► Researcher (revision)
       │ PASS
       ▼
[Stage 2: Content Scanning]  ──FAIL──► Researcher (revision)
       │ PASS
       ▼
[Stage 3: Auditor Review]   ──ESCALATE──► PM (decision needed)
       │ PASS                ──REVISE───► Researcher (revision)
       ▼
PM Final Approval (if needed for deps/questions)
       │
       ▼
Coder receives validated packet
```

## 7. Versioning and Evolution

The schema uses strict versioning (`schema_version: "1.0.0"`). When the schema evolves:

- **Patch** (1.0.x): New optional fields, relaxed constraints. Old packets remain valid.
- **Minor** (1.x.0): New required fields with defaults, new enum values. Migration script provided.
- **Major** (x.0.0): Breaking changes. Old packets must be regenerated.

The `packet_meta.schema_version` field is validated as a `const` — the platform rejects packets that don't match the currently deployed schema version. This prevents version-mismatch bugs where a Researcher trained on v1 produces packets consumed by a Coder expecting v2.

## 8. Future Considerations

- **Packet Signing**: Cryptographically sign the Context Packet after Stage 2 validation. If any byte changes between validation and Coder consumption, the signature breaks and the packet is rejected. This defends against in-memory tampering in a compromised orchestration layer.
- **Packet Diffing**: When a packet is revised (via `parent_packet_id`), automatically generate a diff showing what changed. The Auditor reviews only the delta, not the entire packet.
- **Schema Registry**: As the platform matures, maintain a versioned registry of Context Packet schemas so that older tasks can be audited against the schema version they were built with.
